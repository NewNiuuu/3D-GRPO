## E001 留出集从无到有：为什么必须按点云分组切

**日期**：2026-08-16 → 2026-08-17

### 现象

想知道 RL 有没有提升，去仓库里找测试集，**没有**。`data/` 下两个数据集都只有 train split，
训练配置又是 `max_samples: null`（全量参与训练）。`data/grpo_test.json` 名字有误导性，
它其实是 AirCop 的训练数据。所以此前所有"accuracy 涨了"的说法都无法证明泛化。

### 假设

随手按条目随机二八分就能得到留出集。

### 实验

统计 UrbanVideo 的题与点云的对应关系。

### 结果

```
3251 条题  ->  927 个点云     平均 3.5 题/云，最多 11 题/云
```

按条目随机切，同一个场景会同时出现在训练和测试两边——测试集里的点云模型在训练时见过，泄漏。

另外两个来源的难度差 13 个百分点（AerialVLN 0.836 / EmbodiedCity 0.965），
不分层的话测试集里两者的比例每次都在漂，总分跟着漂。

### 结论与动作

写 `split_holdout.py`：**按点云分组 + 按来源分层**，seed 42 确定性，可随时重现。

```
--test_ratio 0.2  ->  train 3251 条 / 927 云，test 829 条 / 232 云，点云交集 0
```

检测下限（McNemar，n=829，双侧 p<0.05）：分歧率 5% 时需净提升 ≥1.7 分，10% 时 ≥2.3 分，20% 时 ≥3.2 分。
**"不显著"不等于"没提升"**，小于这个量级的改进本来就测不出来。

> ⚠ 这个留出集只保证"没参与 GRPO"，**它 100% 参与过 SFT**。见 [E007](#e007-选项置换拆开-875-分的三个来源)。

## E002 评测点云重采样 bug：base 和 ckpt 看到的不是同一朵云

**日期**：2026-08-17

### 现象

`config` 里 `max_points: 16384` 会对超限点云做均匀随机下采样。抽 16 个文件量了一下点数：

```
p25 9858   p50 20290   p75 33599   max 61446
```

**62%（10/16）的点云会触发封顶**，被截掉的部分保留 59.0%（均值）/ 26.7%（最差）。

### 假设

`eval_mcq.py` 从没调用过 `torch.manual_seed`，各 ckpt 又是并行在不同进程里跑的——
那 base 和 ckpt 面对的很可能是**同一个文件的不同 16384 个点**，对比里混进了重采样噪声。

### 实验

给 `load_point_cloud_tensor` 加 `sample_seed`，用 `zlib.crc32(path)` 而非 Python 内置 `hash()`
（后者对 str 是**逐进程加盐**的，跨进程不确定，不能用）。同一份文件在两个 PID 里各算一次 md5。

### 结果

```
sample_seed=0     PID-A 08fb59ed7de08715   PID-B 08fb59ed7de08715   ✅ 一致
sample_seed=1     5be01268496f388c         5be01268496f388c         ✅ 一致
sample_seed=None  1236595c170e5e0b         d2b71bea0c546c8e         ❌ bug 复现
```

### 结论与动作

已修（`spatiallm_grpo_utils.py` + `eval_mcq.py --seed`，`--seed` 同时决定抽哪些题和抽哪些点）。
**修复之前的评测绝对值不可与修复之后的对比**，base 必须和 ckpt 一起重跑。

顺带记一笔：SFT 侧 `mm_plugin.py:91-100` 的 `_preprocess_point_cloud` 只做 GridSample、
**没有点数上限**，所以 SFT 看到的是全分辨率点云，RL 看到的是封顶后的——存在分布不一致。
提高 `max_points` 受显存限制（峰值已 36.8/39.5 GB）。

## E003 lr 提 5 倍 + 5 epoch：留出集与训练集双双没涨

**日期**：2026-08-17 训练，2026-08-18 评测

### 现象

上一轮 lr=1e-6 跑 128 步，ckpt 之间 `‖ΔW‖/‖W‖` 只有 1e-5 量级，比 fp32→bf16 的量化噪声底
（1.6e-3）还小两个数量级，1000 条里 996~999 条预测完全一致——**权重根本没动**。

### 假设

lr 太小。提到 5e-6、epoch 提到 5（510 步），应该能看到变化。

### 实验

`config_urbanvideo_holdout.yaml`：lr 5e-6 / 5 epoch / G=8 / kl_coef 0.04 / max_points 16384，
8 卡跑满 510 步。评测：base + 4 个 ckpt 各占一张卡并行，同一批题、`--seed 0`、贪心解码。

> ⚠ 踩坑：`save_steps=125` + `save_total_limit=4` 本以为会留下 125/250/375/500，
> 但训练结束时 HF 在 step 510 又存了第五个，limit 保留最后四个，**把 checkpoint-125 挤掉了**。
> 下次要么 limit 调到 5，要么 save_steps 设成能整除总步数的值。

```bash
S=/home/aiscuser/nyp/saves/grpo_urbanvideo_holdout
i=0; for M in /home/aiscuser/nyp/ckpts/point_mixed_downsample $S/checkpoint-{250,375,500,510}; do
  CUDA_VISIBLE_DEVICES=$i python grpo/eval_mcq.py \
      --config grpo/config_urbanvideo_eval_test.yaml -n -1 --seed 0 \
      --ckpt $M --dump /tmp/ev_h_$(basename $M).jsonl & i=$((i+1)); done
cat /tmp/ev_h_*.jsonl > /tmp/ev_h_all.jsonl
python grpo/compare_ckpts.py /tmp/ev_h_all.jsonl
```

### 结果

| ckpt | 留出集 829 条（未参与 GRPO） | 训练集 829 条（参与训练） |
|---|---|---|
| base (SFT) | **0.8818** | 0.8709 |
| checkpoint-250 (ep2.45) | 0.8818 | 0.8661 |
| checkpoint-375 (ep3.68) | 0.8854 | 0.8721 |
| checkpoint-500 (ep4.90) | 0.8842 | 0.8661 |
| checkpoint-510 (ep5.00) | 0.8782 | 0.8673 |

McNemar 全部 **p > 0.1**。最好的 ckpt-375 vs base：分歧 29 题，b=13 / c=16，净差 −3，p=0.7111。

分来源（留出集）：

| ckpt | AerialVLN (536) | EmbodiedCity (293) |
|---|---|---|
| base | 0.8433 | 0.9522 |
| ckpt-250 / 375 / 500 / 510 | 0.8414 / 0.8470 / 0.8451 / 0.8358 | 0.9556 ×4（比 base 多 1 题） |

预测字母分布稳定，无选项塌陷；`parse_fail_rate` = 0。

### 结论与动作

**训练集上也没涨**，所以不是过拟合，是根本没学到。与 base 的分歧率 3.1~3.7%
（上一轮只有 0.1~0.4%）——权重这次确实动了，但方向是随机的（b≈c）。
问题不在 lr，往下查 → [E004](#e004-wandb-的-accuracy-在骗人涨的是确定度不是能力)。

## E004 wandb 的 accuracy 在骗人：涨的是确定度不是能力

**日期**：2026-08-18

### 现象

wandb 上 `train/grpo/accuracy` 一路上涨，但 E003 显示实际能力没变：

| epoch | accuracy | KL(有梯度步) | frac_nonzero_adv | reward_std | 题见过几次 |
|---|---|---|---|---|---|
| 1 | 0.8227 | 0.0386 | 0.2772 | 0.1196 | 0（全新） |
| 2 | 0.8768 | 0.3957 | 0.1740 | 0.0729 | 1 |
| 3 | 0.9248 | 0.3387 | 0.0934 | 0.0385 | 2 |

### 假设

`grpo/accuracy` 是 **T=1.0 采样**的准确率，不是贪心准确率。如果策略只是变得更确定
（熵下降）而 argmax 不变，采样准确率会向贪心准确率收敛并上涨，而真实能力纹丝不动。

> 先排除了一个更简单的解释：epoch 2、3 的题模型已经训过，涨幅可能来自记忆。
> 但 E003 显示训练集贪心准确率也没涨，所以记忆解释不成立。
>
> 另外记一个方法论教训：我一度按 epoch-1 内部分 4 段看到 `0.8163→0.8812→0.8150→0.7800`，
> 判断"泛化在下滑"。分 6 段后是 `0.775→0.859→0.908→0.767→0.862→0.763`，
> 波动幅度 ±0.07 是二项噪声（±0.015）的 4~5 倍——因为切分按点云分组，
> 一个 batch 的 32 题常来自少数几个场景，**批次难度方差远大于策略变化**。
> 回归斜率 t≈−0.4，完全不显著。**段内趋势在这个数据上读不出来，别读。**

### 实验

同一批 300 道训练集题，同一个 ckpt，同时测贪心和 T=1.0 采样 8 条（脚本 `/tmp/gs_probe.py`，临时）。

### 结果

| | 贪心（真实能力） | 采样@T=1.0（wandb 测的） | 差值 ≈ 熵 |
|---|---|---|---|
| base | **0.8867** | 0.7983 | 0.0883 |
| checkpoint-375 | 0.8633 | 0.8542 | 0.0092 |
| checkpoint-510 | **0.8600** | 0.8562 | 0.0038 |

采样准确率涨的 5.8 分**全部来自熵坍缩**；贪心准确率反而掉了 2.7 分。

### 结论与动作

`train/grpo/accuracy` 是「能力 × 确定度」的混合物，熵坍缩时会系统性地骗人。**不能用它判断训练好坏。**

机制：0/1 单 token 回报 + 组内零方差跳过（`std<=1e-6 → continue`，答对的题直接退出损失函数，
没有任何回复力维持它）+ `kl_coef=0.04` 在 KL=0.41 时只贡献 0.016 惩罚（形同虚设）
→ 唯一稳定的梯度方向就是"对已有答案更确定"。

**动作（未实施）**：训练脚本加两项监控——① 每 25 步在固定探针集上跑**贪心**准确率；
② log 策略熵 `H = -Σp log p`。没有这两条，任何超参搜索都在优化假指标。

## E005 权重到底动了多少、动在哪

**日期**：2026-08-18

### 现象

E003 显示预测变了 3%，但不知道权重变化的量级和分布。

### 实验

直接读 safetensors 算 `‖ΔW‖/‖W‖`（全局和按模块）。

### 结果

```
ckpt        ‖ΔW‖/‖W‖ (vs base)
250          1.018e-03      <- 前 250 步走完了 77%
375          1.045e-03
500          1.065e-03
510          1.067e-03

250 -> 510   2.335e-04      <- 后 260 步只走了前 250 步的 23%
```

按模块（vs base，checkpoint-510）：

| 模块 | 参数量 | ‖ΔW‖/‖W‖ |
|---|---|---|
| 点云 backbone (Sonata) | 108.8M | **2.566e-03** |
| 点云投影层 point_proj | 1.3M | 1.859e-03 |
| embed_tokens | 310.6M | 1.589e-03 |
| LLM 主干 (Qwen3 layers) | 1409.4M | 9.681e-04 |

单层相对变化最大的一直是 `point_proj.0.bias`（step 510 时 0.192）。

### 结论与动作

1. **lr 不是太小**（比上一轮大 100 倍），后半程权重几乎不动是因为**梯度断供**——
   熵坍缩后组内全对，`std<=1e-6` 直接 continue。第 250 步之后的 260 步基本在空转，
   这轮浪费约 55 分钟。
2. **相对扰动最大的是 3D 编码器**，是 LLM 主干的 2.7 倍。用一个"答案字母对不对"的标量
   去扰动空间编码器——这个信号里没有任何空间信息。E004 里贪心准确率掉的 2.7 分大概率来自这里。
   **动作（未实施）**：RL 阶段冻结点云 backbone，或给它 1/10 的 lr。

## E006 点云消融：换成不相干的场景，准确率只掉 0.75 分

**日期**：2026-08-18

### 现象

E003~E005 一路排查下来，训练本身没有明显 bug，但就是学不到东西。开始怀疑任务本身。

### 假设

模型可能根本没在用点云——如果决策路径不经过点云，RL 的梯度自然无处着力。

### 实验

**把点云换成完全不相干的另一个场景的点云**，其他一切不变（同一道题、同一个 base 模型、贪心解码），
比较准确率和输出一致率。脚本 `/tmp/pcd_ablate.py`（临时），n=400。

### 结果

| 数据集 | 正确点云 | 错配点云 | 掉幅 | 两者输出**逐字相同** |
|---|---|---|---|---|
| UrbanVideo（留出集） | 0.8750 | 0.8675 | **−0.0075** | **95.75%** |
| AirCop Sim | 0.9425 | 0.9200 | −0.0225 | 97.25% |
| AirCop Real2 | 0.8825 | 0.8650 | −0.0175 | 96.25% |

### 结论与动作

**模型 96% 的回答与点云无关。** 这一条解释了前面所有现象：
GRPO 优化的 0/1 回报，其决策路径不经过点云，梯度只能沿文本捷径走，最终退化成熵坍缩。

**不是奖励函数不够稠密——是回报没有引用点云。** 把 0/1 改成软概率不解决任何问题。

往下查两个方向：捷径具体是什么（→ [E007](#e007-选项置换拆开-875-分的三个来源)）、
数据为什么会这样（→ [E008](#e008-数据审计两个数据集为什么答不出来)）。

## E007 选项置换：拆开 87.5 分的三个来源

**日期**：2026-08-18

### 现象

E006 证明点云没被使用，那 87.5 分从哪来？"模型记住了答案"有两种完全不同的形态：
①记住了"这道题选 B"（字母记忆）；②靠选项**文本本身**判断（干扰项是自动生成的，可猜）。

### 实验

把选项**左旋一位**（每个选项都换到不同字母）、GT 字母跟着重映射，跑三种条件：
原顺序+正确点云 / 置换+正确点云 / 置换+错配点云。脚本 `/tmp/perm_test.py`（临时），n=400，贪心。

### 结果

| 条件 | UrbanVideo | AirCop Real2 | AirCop Sim |
|---|---|---|---|
| 随机基线 | 0.2087 | 0.2500 | 0.2500 |
| 置换 + **错配**点云（≈纯文本） | 0.6875 | 0.6350 | 0.6150 |
| 置换 + 正确点云 | 0.7025 | 0.6525 | 0.6275 |
| 原顺序 + 正确点云（**一直在报的分数**） | **0.8750** | **0.8825** | **0.9400** |
| 置换后仍选同一字母 | 0.090 | 0.175 | 0.215 |

拆成三块（百分点，相对随机基线）：

| 贡献来源 | UrbanVideo | Real2 | Sim |
|---|---|---|---|
| ① 选项文本本身可猜（不看点云、打乱顺序也能对） | **+47.9** | **+38.5** | **+36.5** |
| ② 选项位置 / 字母先验 | +17.3 | +23.0 | +31.3 |
| ③ **点云真正的贡献** | **+1.5** | +1.8 | +1.3 |

位置先验的指纹（AirCop Real2）：

```
GT 分布            A 42.0%  B 28.6%  C 16.7%  D 12.8%
模型预测（原顺序）  A 43.0%  B 28.5%  C 16.0%  D 12.5%   <- 几乎逐位对齐
模型预测（置换后）  A 42.3%  B 18.0%  C 18.0%  D 21.8%   <- 正确答案已轮到 D，它还在答 A
```

各数据集的众数基线（全答最常见的字母）：UrbanVideo 0.215，AirCop 各 split **0.414~0.461**。

### 结论与动作

**87.5 分里，点云只值 1.5 分。**

- 第②块（17~31 分）**是过拟合**，而且是对数据集 artifact 的过拟合，SFT epoch 越多越严重。
- 第①块（37~48 分）**不是过拟合，是数据集本身的缺陷**——干扰项在措辞、具体程度、长度上
  与正确答案有系统差异，任何语言模型不看点云都能挑出来（VQA 经典的 language prior）。

**两个诚实的保留**：
1. 手上没有 SFT 之前的权重，**无法区分第①块里多少是 SFT 教的、多少是 Qwen3 自带的**。
   要分清得拿原始 SpatialLM 基座跑同样的三条件。
2. 置换后的格式模型没见过，17~31 分的下降里可能混有"格式陌生"的成分。不过"置换后仍选同一字母"
   只有 9%~21%（纯字母记忆应接近 100%），说明模型确实在跟内容走，主体还是位置先验。

**动作**：今后任何评测**必须同时报「选项置换」和「错配点云」两条基线**，否则数字不是能力数字。
此前所有 0.88 vs 0.885 的比较都无意义——和点云有关的信号量只有 1.5 分，噪声都比它大。

## E008 数据审计：两个数据集为什么答不出来

**日期**：2026-08-18

### 现象

E006/E007 证明点云没被使用。往上追一层：是模型不会用，还是题目本身不需要点云？

### 实验

直接读原始 JSON 和磁盘上的 .ply，做统计 + 逐条看具体样例。

### 结果

#### 两个数据集是**两种不同的问题**，只有 AirCop 是真正的"错配"

| | AirCop | UrbanVideo |
|---|---|---|
| 点云与题的配对 | **错的**（UAV2 的题配 UAV1 的云） | **对的**（就是那个场景） |
| 就算配对全修好 | 仍不可答——另一个视角的数据不存在 | 仍不可答——轨迹/时序信息在转换时丢了 |
| 性质 | 数据管线 bug | 模态转换的固有信息损失 |

#### AirCop：记录自身就自相矛盾

```json
{
 "id":            "23-00000001_MDMT_when2col_UAV2_1",        <- 说这是 UAV2 的题
 "question_type": "4.1 When to Collaborate (UAV2)",          <- 又说一次是 UAV2
 "point_clouds": ["/Pointcloud-VQA/AirCopBench/Real2_VQA_train/
                   23-00000001_MDMT_when2col_UAV1_1.ply"],   <- 给的却是 UAV1 的点云
 "conversations": [{"from":"human","value":"<point_cloud>\nShould UAV2 collaborate with
   another UAV to enhance perception of the scene due to limited coverage of specific areas? ..."}]
}
```

磁盘上每个场景**只有一个机位**的 ply，一个都不多：

```
Real2_VQA_train   230 个 ply, 场景组 230, 每组机位数 {1: 230}
Sim3_VQA_train    609 个 ply, 场景组 609, 每组机位数 {1: 609}
Sim5_VQA_train     47 个 ply, 场景组  47, 每组机位数 {1:  47}
Sim6_VQA_train     49 个 ply, 场景组  49, 每组机位数 {1:  49}
```

原因：AirCopBench 原本是多机位**图像** benchmark，转点云时每个场景只生成/保留了一份 ply，
然后把所有机位的题都指向了它。上面那朵 `UAV1_1.ply` 被 **15 道题**共用，其中包括：

- "Which object in **UAV2** corresponds to the white van traveling on the road in **UAV1**?"（跨视角匹配，只有一个视角）
- "What is the perception quality assessment score for **the image captured by UAV2**?"（给一张没提供的图打分）
- "How does the visibility differ **between the two UAV perspectives**?"（要比较两个视角）
- "...near **the bottom right corner of the image**?"（点云是三维的，没有 image，也没有"右下角"）

按视角需求分类全部 24870 条（正则启发式，非精确）：

| | 条数 | 占比 |
|---|---|---|
| 需要 ≥2 个机位视角 | 8374 | 33.7% |
| 引用 image / 画面区域（点云无此概念） | 9334 | 37.5% |
| 单视角原则上可答 | 7162 | **28.8%** |

#### UrbanVideo：配对是对的，但时序信息在转换时丢了

以 `EmbodiedCity_11.ply`（672 万点、108MB）为例，配对完全正确，但它的 11 道题全在问飞行轨迹：

```
[C] Where do you start and end your journey?
[B] Which takes longer, your ascent between the skyscrapers or your descent to align with the 22nd floor?
[A] How does the distance between you and the cone-shaped structure change after you turn to the right?
[C] Thinking back on past Action Generations and objects you've seen, ...
[F] At the initial position, ... What is your next move?
```

UrbanVideoBench 原本是**视频** benchmark。转点云是把视频里看到的**内容**聚合成一朵静态点云，
**相机轨迹被丢掉了**。点云里没有起点、当前位置、朝向、经过的时间、看过什么的历史。
全集统计：**94.6%（3075/3251）的题含自我轨迹或时序线索**
（`as you` / `your` / `takes longer` / `before` / `after`）。

#### 点云里到底有什么

两个数据集的 .ply header 都只有：

```
property float x / y / z
property uchar red / green / blue / alpha
```

**没有语义标签、没有实例 ID。** 程序化生成题目只能基于纯几何量（高度、范围、点数、方位、距离、颜色聚类）。

#### 规模与答案分布

| 数据集 | 条数 | 点云数 | 题/云 | 众数基线 |
|---|---|---|---|---|
| UrbanVideo MCQ | 3251 | 927 | 3.5 | 0.215 |
| AirCop Real2 | 2286 | 230 | 9.9 | 0.420 |
| AirCop Sim3 | 8435 | 609 | 13.9 | 0.461 |
| AirCop Sim5 | 1009 | 47 | 21.5 | 0.456 |
| AirCop Sim6 | 1848 | 49 | 37.7 | 0.414 |
| AirCop Sim | 11292 | 705 | 16.0 | 0.453 |

### 结论与动作

**在这两个数据集上调奖励函数和超参没有意义，天花板就是那 1.5 分。**

AirCop 的错配理论上可以靠重新生成多机位 ply 来修；UrbanVideo 的问题**修不了**，
除非把相机轨迹作为额外输入（比如编码成位姿 token 拼进 prompt）——那是改任务定义，不是改数据。

## 当前结论汇总

按因果链从表到里：

```
留出集/训练集 accuracy 都没涨 (E003)
  └─ wandb 上却在涨 —— 那是熵坍缩，贪心准确率反而掉 2.7 分 (E004)
      └─ 后半程权重几乎不动 —— 组内零方差，梯度断供 (E005)
          └─ 为什么组内总是全对？因为答案由文本决定，不由点云决定 (E006: 换点云只掉 0.75 分)
              └─ 87.5 分 = 47.9 文本捷径 + 17.3 位置先验 + 1.5 点云 (E007)
                  └─ 因为题目问的信息根本不在点云里 (E008)
```

**一句话**：不是 RL 没调好，是任务在当前数据形式下没有可优化的信号。

### 由此确定的方向

| 方向 | 判断 |
|---|---|
| 加大 lr / 加 epoch | ❌ 无效，梯度在第 250 步就断了 |
| 把 0/1 回报改稠密（软概率） | ❌ 不解决"回报不引用点云" |
| 提高采样温度增加组内方差 | ❌ 当前实现 sample 用 T、算 logp 用 T=1，会引入未校正的 off-policy 偏差 |
| 对比接地回报（正确点云 vs 错配点云的 logp 差） | ⚠ 原理正确，但在现有数据上天花板只有 1.5 分 |
| 选项置换不变性回报 | ⚠ 能打掉 17~31 分的位置先验捷径，但打不出新能力 |
| **程序化生成几何题（RLVR）** | ✅ **唯一有意义的方向**——答案由 .ply 的 xyz+rgb 算出来，文本先验和位置先验都无从下手 |
| 冻结点云 backbone / 降其 lr | ✅ 独立于上面，应该做（E005） |
| 加贪心准确率 + 策略熵监控 | ✅ 独立于上面，必须做（E004） |

## 待验证的问题

1. **SFT 前的基座在三条件下是多少分？** 拿原始 SpatialLM 权重跑 E007 的三条件。
   若"置换+错配点云"也有 0.6 左右，说明那 40 分纯粹是数据集缺陷；若接近随机，说明 SFT 放大了捷径。
